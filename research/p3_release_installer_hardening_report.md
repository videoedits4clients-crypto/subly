# P3 — Release & Windows Installer Hardening (Task ID 47216)

## 1. Executive summary

This phase audited SUBLY's complete Windows packaging and distribution pipeline — from source
through `next build`, the frozen Whisper worker, the bundled FFmpeg/ffprobe binaries, the NSIS
installer, and uninstall — and hardened it into a genuine release candidate. The audit-first pass
(§2–§3) found the packaging architecture to be, in most respects, already careful and
well-engineered: per-user data paths correctly separated from the read-only install directory,
first-run database bootstrap from a pre-migrated template, additive schema migrations that never
touch existing rows, a frozen Python-free transcription worker, deliberate process-tree kills that
account for PyInstaller's onefile bootloader, and a font preflight system that refuses to silently
substitute a missing font. None of that was rewritten.

Live testing against real, freshly-built installers (not just source-reading) surfaced **six
confirmed, demonstrated problems**, each traced to its root cause before being fixed:

1. **Real developer test media, full application source, and dev-only config were shipping inside
   every installer** — confirmed by inspecting an actual packaged build's `resources/app-server`
   directory: 4.1MB of leftover QA videos/exports, the complete uncompiled TypeScript source tree,
   and a `.env` file whose hardcoded `AUTH_SECRET="dev-only-insecure-secret-change-me"` every
   single installed copy of SUBLY would have loaded identically.
2. **Removing that `.env` (the fix for #1) broke NextAuth entirely** — every page navigation
   started logging a `MissingSecret` error, since nothing else in the packaged app ever set
   `AUTH_SECRET`. Caught immediately via a live stdout-captured launch, fixed at the source: a
   fresh random secret generated by Electron at every launch.
3. **The packaged Whisper transcription worker attempted a live network call on every single
   transcription, even for a model already fully cached locally** — confirmed via code reading and
   fixed with `local_files_only=True` once the local cache-hit check passes; the docstring already
   claimed this was a no-op, but nothing enforced it.
4. **The font-fetch network call used to satisfy an uncached font had no timeout at all** — a
   genuinely offline machine that drops packets rather than refusing the connection could hang an
   export indefinitely, defeating the whole point of the font-preflight system's fast, clear error.
5. **A deliberate "one transcription at a time per sidecar" rejection (confirmed intentional, well
   documented, and NOT rewritten) had its specific, useful error message discarded** in favor of a
   generic "Something went wrong," reproduced live by uploading two videos concurrently.
6. **The installed app exposed no version information anywhere** — confirmed by grepping the whole
   app; fixed by baking the version into the existing sidebar text rather than adding a new screen.

Every fix was verified against a genuinely fresh, freshly built installer — not just re-read as
source. A full 30-step release-candidate workflow, an offline test with the actual Hugging Face
endpoint pointed at an unreachable address, a real crash/kill-and-relaunch test during both
transcription and export, an in-place upgrade install, path-with-spaces and path-with-Unicode
installs, and an uninstall all passed. Production data is confirmed byte-for-byte unchanged
(Project, ExportJob, Subtitle, VideoAsset, and SubtitlePreset tables all compared row-for-row, not
just counted).

## 2. Packaging architecture

Traced directly from source (`electron/main.js`, `next.config.ts`, `package.json`'s `build` block,
`scripts/postbuild-standalone.js`, `scripts/electron-builder-after-pack.js`), then confirmed by
inspecting a real packaged build's actual directory tree — not assumed from the build succeeding.

**Lifecycle**: `next build` (Turbopack) produces `.next/standalone` — a self-contained Node server
(only the traced `node_modules` it needs). `scripts/postbuild-standalone.js` then copies in
`.next/static`, `public/`, `prisma/template.db`, the offline font-cache seed, and the frozen
`whisper-worker.exe`, and (per §19 below) now also strips dev-only cruft Next's tracer swept in.
`electron-builder` packages `electron/**/*` (asar'd) as the app shell and copies the entire
`.next/standalone` tree via `extraResources` to `resources/app-server` (never asar'd — confirmed
by inspecting a real build: `resources/app-server` sits on disk as plain files, so the ffmpeg/
ffprobe/whisper-worker binaries in it stay directly executable). A custom `afterPack` hook then
restores `node_modules` into `app-server` (electron-builder's own file matcher silently drops
`node_modules` even from `extraResources` — confirmed via `release/builder-debug.yml`), since the
Next standalone server can't start without its own copy of the `next` package. NSIS produces the
final installer (`oneClick: false`, `allowToChangeInstallationDirectory: true`, no `perMachine` —
confirmed by a real build log: `perMachine=false`, i.e. a per-user install needing no admin
rights).

**Electron main process** (`electron/main.js`): picks a fresh OS-assigned port every launch
(`net.createServer().listen(0, ...)`), resolves `resourcesRoot` via `app.isPackaged` (packaged:
`process.resourcesPath/app-server`; dev: the repo's own `.next/standalone`), spawns the standalone
`server.js` via Electron's own bundled Node (`ELECTRON_RUN_AS_NODE: "1"`), and polls
`/api/system/status` until it's up (30s timeout). All per-user data paths
(`appDataPaths()`) are derived from `app.getPath("userData")` — never the install directory.

**First-run bootstrap**: `ensureDatabase()` copies a pre-migrated, empty `prisma/template.db` into
place rather than shelling out to a Prisma CLI (not bundled in a packaged build — confirmed by
trying it, per the code's own comment). `electron/db-migrations.js` then runs a small, hand-rolled,
additive-only migration runner (`node:sqlite`, no new dependency) on every launch — detects
"already applied" by inspecting the database's own live schema via `PRAGMA table_info`, never a
separate version ledger, and only ever does `ALTER TABLE ... ADD COLUMN`, all in one transaction,
rolling back cleanly on any failure. `ensureFontsCacheSeed()` similarly seeds the per-user
fonts-cache directory from a bundled pre-fetched set so a normal export never needs the network for
SUBLY's built-in fonts.

**Runtime dependency identification is corrected here versus what static reading alone would
suggest.** `ffmpeg-static` and `@ffprobe-installer/ffprobe` are declared in `next.config.ts`'s
`serverExternalPackages` (kept out of Turbopack's JS bundle since they ship native binaries). Live
testing (§8) confirmed Turbopack additionally externalizes them into their **own,
content-hash-named copies inside `.next/node_modules/`** (e.g.
`resources/app-server/.next/node_modules/ffmpeg-static-<hash>/ffmpeg.exe`) — a *third* physical
copy, independent of both the source repo's `node_modules/ffmpeg-static` and the packaged app's
regular `resources/app-server/node_modules/ffmpeg-static`. This is the copy actually spawned at
runtime; the regular `node_modules` copy (restored by the `afterPack` hook for the `next` package's
sake) is not used for these two specific binaries. See §8 and §19 for the size implication.

## 6. Offline QA

Network connectivity to the app's one real optional dependency (Hugging Face, for Whisper model
downloads) was blocked by launching the packaged app with `HF_ENDPOINT` pointed at an unreachable
local address (`http://127.0.0.1:1`) — the standard, documented `huggingface_hub` override for
exactly this kind of air-gapped testing, and a more surgical, reversible approach than disabling
the whole machine's networking (which would also have disconnected this session's own tooling).

With the endpoint unreachable and the default "small" model already cached from earlier sessions:

- **Create project → upload → transcribe**: completed successfully in ~27s, no hang, no error —
  this specifically exercises the fix in §19.1 (previously this would have attempted a live network
  call on every transcription even though the model was already fully cached).
- **Style is fine by default, export succeeds offline**: a freshly created, never-touched project
  (default style — one of SUBLY's built-in preset fonts, already in the offline-seeded font cache)
  exported successfully (`DONE`/`complete`) with the network still blocked.
- **Playback**: video and generated export both play back from local disk; no network involved by
  design (confirmed by reading `src/lib/storage/local.ts` — local files served via
  `/api/files/[...key]`, no external URL ever constructed).
- **Restart → reopen**: app relaunched (still offline) and the transcribed/exported project reopened
  with all data intact.

**One real, narrow, already-partially-mitigated offline gap remains and is documented rather than
built around** (§19.2, §20): a font/weight combination **outside** the 16 pre-seeded built-in fonts
still needs one live Google Fonts fetch the first time it's used. This was already caught before
silently degrading (`preflightExportFonts`, from a prior phase, refuses to start an export with an
unresolvable font) — the fix this phase adds is bounding that fetch with a 5-second timeout so a
genuinely offline machine fails fast with a clear error instead of risking an indefinite hang.
Building a fully offline font system (bundling every weight of every listed font) was judged clearly
out of scope — a new-infrastructure undertaking the task explicitly says not to add.

## 7. Whisper worker QA

Tested against the real, frozen, PyInstaller-built `whisper-worker.exe` in the packaged app — never
against `python/whisper_worker.py` run under a system Python.

- **Executable exists, correct path resolved**: confirmed via `electron-debug.log`'s
  `frozen worker exe found at <path inside the installed app>` on every launch.
- **Worker starts, receives input, produces a transcript**: real English audio transcribed
  correctly multiple times this phase (RC checklist, offline test, crash-recovery test).
- **Progress reaches the UI**: `TRANSCRIBING` status with live `progress` polled correctly.
- **Cancellation**: `local-whisper-sidecar.ts`'s cooperative-cancel-then-hard-kill design
  (unchanged this phase, already well-engineered — a bounded grace timer escalates to a full
  process-tree kill only if the cooperative check doesn't respond in time) was read in full; not
  re-exercised destructively this phase since Task 91463 already covered it and no regression was
  found or suspected.
- **Worker termination / orphan cleanup**: force-killed `SUBLY.exe` mid-transcription (confirmed via
  `tasklist` that `whisper-worker.exe` was genuinely running at kill time) — after the kill, **no
  orphaned `whisper-worker.exe` process remained** (Windows Job Object semantics cascade the kill to
  the whole process tree Electron spawned, independent of the app's own explicit
  `taskkill /t` cleanup, which only runs on a *graceful* quit).
- **Transcription failure surfaces correctly**: reproduced live by uploading two videos
  concurrently — the sidecar's own deliberate one-decode-at-a-time guard
  (`python/whisper_worker.py`, confirmed intentional, NOT modified) rejected the second with a
  specific message that was previously being discarded into a generic one (fixed, §19.3).
- **Worker restart after failure / app relaunch still works**: confirmed via the crash-during-
  transcription test (§11) — relaunching after an abrupt kill starts a fresh worker process
  correctly and transcribes subsequent projects normally.
- **No silent fallback to Python/system binaries**: confirmed structurally
  (`electron/main.js` refuses to even start the server in a packaged build with no frozen worker
  present — "This installation appears to be corrupted") and confirmed live (every transcription
  this phase resolved to the bundled `.exe` path, never a system `python`).

## 8. FFmpeg/ffprobe QA

- **Path resolution**: corrected understanding from static reading (§2) — the actual runtime
  binary is a Turbopack-externalized copy under `resources/app-server/.next/node_modules/
  ffmpeg-static-<hash>/ffmpeg.exe`, confirmed by a live, iterative unavailability test (below).
- **Video probing**: every upload this phase (including all four path-edge-case filenames, §10)
  successfully probed via ffprobe (`VideoProbe.duration` etc. populated correctly).
- **Waveform/audio extraction**: exercised as part of every transcription this phase
  (`extractAudio()` → 16kHz mono WAV → fed to the Whisper worker) — worked correctly throughout.
- **Export**: 720p/1080p/4k, multiple fps/quality combinations, all completed successfully across
  dozens of exports this phase.
- **Output verification**: unchanged from the already-PASSed Task 91463 pipeline; not re-audited in
  depth here (out of this phase's scope, no regression suspected or found).
- **Cancellation**: `POST .../export/:id/cancel` on a slow 4K/max-quality export returned
  `{"cancelled":true}`, the job reached a terminal `ERROR` state with `errorMessage: "Export
  cancelled."` (distinct from a real failure), and — confirmed directly — **no orphaned partial
  output file and no orphaned `ffmpeg.exe` process** remained afterward.
- **Failure handling — binary temporarily made unavailable (controlled, disposable, reversed
  after)**: renamed the actual runtime `ffmpeg.exe` (the `.next/node_modules` copy identified
  above) away, relaunched fresh, triggered an export. Result: job reached `ERROR` status
  (`stage: "rendering"`, `progress: 3`) with the friendly message **"Something went wrong while
  exporting your video."** — no leaked file path, no raw stack trace shown to the user — while the
  full technical detail (`Error: spawn <exact path> ENOENT`, `errno: -4058`, `code: 'ENOENT'`) was
  captured in the server's own stdout log for a developer to diagnose. The binary was restored
  immediately after this one test and re-confirmed present before any further QA. (An earlier
  attempt renaming only the *unused* regular-`node_modules` copy of the binary — both in the
  packaged app and the dev repo — produced no failure at all, which is exactly what led to
  discovering the real embedded-copy location in the first place; that finding is now folded into
  §2's corrected architecture description.)
- **ffprobe** uses the identical externalization/resolution mechanism (confirmed by directory
  listing: `@ffprobe-installer` sits alongside `ffmpeg-static-<hash>` in the same
  `.next/node_modules`); not independently disabled-and-tested given the mechanism is verified
  identical and the upload route's own 20-second probe timeout (pre-existing, unmodified) already
  independently bounds a hang if it were ever missing.
- No production files were permanently modified — every rename in this section was undone
  immediately after its test, confirmed via a follow-up listing before moving on.

## 9. User-data/path audit

- **Install directory vs. user-data directory**: cleanly separated, confirmed both by reading
  `electron/main.js`'s `appDataPaths()` (everything keyed off `app.getPath("userData")`) and by
  live inspection — nothing is ever written under `resources/app-server` at runtime; every write
  observed during this phase's entire QA landed under `%APPDATA%\subs`.
- **SQLite** (`subly.db`), **uploaded media**, **audio extraction**, **waveform cache** (all under
  `SUBLY_UPLOADS_DIR` → `%APPDATA%\subs\uploads`), **Whisper models**
  (`SUBLY_MODEL_DIR` → `%APPDATA%\subs\models`), **fonts** (`SUBLY_FONTS_CACHE_DIR` →
  `%APPDATA%\subs\fonts-cache`), and **exports** (same uploads root, per-project `exports/`
  subfolder) — all confirmed to live under the per-user app-data directory, never inside
  `Program Files`/the install directory, never in a read-only location.
- **localStorage/crash-snapshot data**: this is Electron `BrowserWindow`'s own per-origin storage,
  which Electron itself places under `userData` automatically — not something SUBLY's own code
  manages a path for; unchanged and unaudited further this phase (no demonstrated problem).
- **Temporary FFmpeg files**: `withTempFile()` (`src/lib/ffmpeg/index.ts`, unmodified) writes the
  export's `.ass` sidecar next to the output and always removes it in a `finally` block regardless
  of success/failure/cancellation — confirmed no orphaned `.ass`/temp file after the cancelled
  export test in §8.
- **Logs**: `%TEMP%\subly-electron-debug.log` — see §15.
- **Paths with spaces**: the entire fresh-install (§4) and upgrade (§12) QA this phase was
  performed against `C:\Users\User\AppData\Local\Programs\SUBLY Test (RC)` — a real space AND
  parentheses in the install path — with zero path-related failures across dozens of launches,
  uploads, transcriptions, and exports.
- **Unicode characters**: a project named `日本語のビデオ` with a matching Unicode video filename
  uploaded, probed, transcribed, exported, and had all three subtitle formats downloaded
  successfully (§10).
- **Long folder names**: not separately stress-tested (no demonstrated problem to chase, and the
  install path used throughout this phase, `SUBLY Test (RC)`, combined with the deeply nested
  `AppData\Local\Programs\...\resources\app-server\.next\node_modules\ffmpeg-static-<hash>\` runtime
  path already exceeds 100 characters with no issue observed).

## 11. Crash/recovery QA

Re-tested specifically from the packaged, installed environment (not the dev server) — the existing
recovery architecture (`lib/recovery/stale-job-recovery.ts` and friends) was **not modified**.

- **Kill during transcription**: uploaded a video, confirmed genuinely mid-`TRANSCRIBING` via a
  live status poll, confirmed a real `whisper-worker.exe` process was running
  (`tasklist`), then force-killed `SUBLY.exe`. No orphaned `whisper-worker.exe` remained.
  Relaunched: the interrupted project correctly reached `status: "ERROR"` with
  `errorMessage: "Previous processing was interrupted. You can retry this project."` — clear,

- **Kill during export**: used a longer (5-minute) source video with a 4K/60fps/maximum-quality
  export specifically to get a wide enough window to catch it mid-render — confirmed
  `stage: "rendering"`, `progress: 6` and a live `ffmpeg.exe` process, then force-killed. No
  orphaned `ffmpeg.exe` remained. Relaunched: the export job correctly reached `ERROR` with
  `errorMessage: "Previous export was interrupted. The incomplete output was removed."` — and this
  claim was independently verified true: the project's `exports/` directory was confirmed **empty**
  after relaunch, no partial `.mp4` left behind.
- **Kill immediately after editing**: exercised as a byproduct of the RC checklist (§17) — an
  editor session with a fresh caption-text edit and an animation change was closed via a full app
  kill and relaunch; both changes were confirmed persisted (the app's save-queue commits edits
  well before any deliberate kill in this testing, consistent with the top bar's own "Saved"
  indicator being visible before each kill).
- **No developer-only recovery path exists**: all of the above ran against the real
  `resources/app-server` packaged code path, using the production `%APPDATA%\subs\subly.db` (backed
  up first, restored to identical state after, §18) — not a dev-mode shortcut.

## 12. Upgrade/reinstall behavior

The installer's own NSIS config (`oneClick: false`, `allowToChangeInstallationDirectory: true`, no
`deleteAppDataOnUninstall`, no custom `.nsh` script — confirmed by reading the full config and
searching the repo for any custom uninstall script, none found) supports installing a newer version
directly over an existing install: NSIS's default "install over" behavior for a `perMachine: false`
target overwrites the application files in place and never touches `%APPDATA%`. This was tested with
a genuine version bump, not just a same-version reinstall:

1. **Version A** (0.1.0): installed to `SUBLY Test (RC)`, created/edited/exported real project data
   via the full RC checklist flow.
2. Closed the app.
3. **Version B** (0.1.1, this phase's fixed build): installed silently to the exact same directory.
   Confirmed the installed `SUBLY.exe`'s timestamp matched the new build exactly (an in-place
   overwrite, not a fresh side-by-side install).
4. Launched Version B: `ensureDatabase()` correctly found the existing database and skipped
   recreating it; `runMigrations()` reported every migration `alreadyUpToDate` (no destructive
   re-migration); the frozen worker path resolved to the new install's own `whisper-worker.exe`.
5. Reopened the pre-upgrade project data: **all 18 projects, 46 export jobs, 0 presets** intact

1. **`python/whisper_worker.py`** — `ensure_model()` now passes `local_files_only=True` to
   `huggingface_hub.snapshot_download()` once the local cache-hit check (`model_is_cached()`)
   already confirms the model is present, so an already-cached model genuinely never attempts a
   network call — matching what the function's own docstring already claimed. Verified live: a
   transcription of an already-cached model succeeded in ~27s with the Hugging Face endpoint

   an export indefinitely. Failures still fall through to the existing, unmodified
   `preflightExportFonts` clear-error path.

3. **`src/lib/pipeline.ts`** (+ new **`src/lib/transcription-status-message.ts`**) — the sidecar's
   deliberate "one transcription at a time" rejection now surfaces as **"Another transcription was

5. **`electron/main.js`** — the spawned Next server is now given a freshly generated random
   `AUTH_SECRET` (`crypto.randomBytes(32).toString("hex")`) on every launch. This is a fix *for a

## 20. Issues intentionally left unchanged / remaining release limitations

- **Two duplicate copies of `ffmpeg.exe`/`ffprobe.exe` ship inside every installer** — the regular
  `resources/app-server/node_modules/ffmpeg-static/ffmpeg.exe` (restored by the existing
  `afterPack` hook, necessary for the `next` package itself) and the Turbopack-externalized
  `resources/app-server/.next/node_modules/ffmpeg-static-<hash>/ffmpeg.exe` (the one actually used
  at runtime, confirmed §8) together account for roughly 166MB of redundant installer size. This is
  a confirmed, real inefficiency, not a functional bug — every export/probe this phase worked
  correctly. Deduplicating it safely would require verifying nothing else depends on the regular
  `node_modules` copy as a fallback resolution path across Next.js's own bundler internals, which is
  a materially different and riskier change than this task's scope justifies for a pure size
  optimization; documented here rather than attempted.
- **A font/weight combination outside the 16 pre-seeded built-in fonts still needs one live network
  fetch the first time it's used** (§6). Already caught by the existing font-preflight system
  before silently degrading; this phase added a timeout so that failure is prompt rather than a
  possible hang. Building a fully offline font library was judged out of scope (new infrastructure,
  not a fix to an existing feature).
- **No SUBLY-branded Windows icon exists** — the installer and executable both use electron-builder's
  generic default icon (confirmed via the build log). A real design asset is needed to fix this;
  none exists in the repository to draw from, and fabricating one is outside a packaging-hardening
  task's remit. Documented as a genuine, if purely cosmetic, release-readiness gap.
- **No formal auto-update mechanism exists** (§12) — accurately documented as the current state, not
  built, per the task's explicit instruction.
- **A `TypeError: Cannot read properties of undefined (reading 'trim')` crash was incidentally
  discovered in the ASS-generation code path** (`src/lib/subtitles/ass.ts`'s `assColorWithAlpha()`)
  when a project's `globalStyle` is missing a required color field. This was reproduced **only**
  through a raw, malformed `PATCH` request sent directly to the API during this phase's own testing
  (replacing the entire `globalStyle` object with a partial one, rather than the real Style panel's
  always-complete object) — never through the actual UI, which was separately confirmed (§17, step
  11) to always send a complete style object. This is a backend input-robustness gap, not a
  packaging/installer issue, and rewriting the export/rendering pipeline's input validation is
  explicitly out of this task's scope; flagged here for visibility rather than fixed.
- **The root cause of the pre-existing stray `UsersUserAppDataRoamingsubssubly.db` file** (deleted
  in fix #6) was traced precisely: it is **not** produced by any SUBLY application code path.
  Reproduced directly this phase — passing a Windows absolute path containing backslashes as an
  inline argument to `node -e` through this environment's Bash tool silently mangles the backslashes
  before Node ever sees them, and Node's `node:sqlite` `DatabaseSync` constructor then creates a
  new, empty database file at the resulting garbage relative path in the current working directory.
  This is an artifact of ad hoc debugging via this specific tooling environment, not a SUBLY defect;
  noted here only because it explains a file that might otherwise look mysterious, and because
  `postbuild-standalone.js`'s hardening (fix #6) now prevents any such stray file from reaching a
  real installer regardless of how it's created.
